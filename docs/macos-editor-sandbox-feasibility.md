# macOS private-editor backend: feasibility stop

**Historical record:** native prototype source and demo tools have been removed.
References to their paths/behavior below are evidence from the earlier review,
not current implementation or runnable acceptance instructions.

**Parked after user course change.** The current workstream is the
[embedded-engine evaluation](embedded-editor-evaluation.md). Do not pursue the
DTS suggestion below as the next task; no request was submitted.

**Result: blocked at mechanism selection, not implemented or natively tested.**
No supported macOS native-process mechanism satisfying the complete
`editorsandbox.NoPersistence()` contract was established by this review. Keep
`Current().Available` false and both protected admission stops intact. This is
not a claim that every possible macOS isolation architecture is impossible.

## Required boundary

Before any private transmission, the backend must own the exact editor process
and intended pipe endpoints, deny filesystem persistence, new processes, network
and unauthorized new IPC, and exclude inherited writable/proxy capabilities.
The parent alone holds SP keys/store access and publishes encrypted saves and
recovery. Container/state/tmp write exceptions and a trusted-editor fallback are
not approved. Paging/core dumps, display capture and compromised OS remain
[explicit exclusions](privacy.md#outside-the-boundary).

## Public-source findings

1. **Supported App Sandbox does not supply this boundary on its own.** Apple's
   [configuration guide](https://developer.apple.com/documentation/xcode/configuring-the-macos-app-sandbox)
   describes kernel enforcement but also read-write container access. Its
   [file-access guide](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)
   explicitly grants "full read and write access" to that container and says the
   app "can run programs located there as well." Omitting optional file-access
   entitlements does not remove these permissions. No documented way to remove
   them while imposing the full required boundary was established here.
2. **Signed helper inheritance does not make that policy stricter.** Apple's
   [embedded-tool guide](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app)
   describes App Sandbox/inherit entitlements, code signing and packaging,
   including Developer ID distribution. These are deployment requirements, not
   no-persistence enforcement. The guide's Intel 10.15/Apple silicon 11.0 example
   targets are not an SP support matrix. The file-access guide also documents
   container/code-signature association changes from macOS 14.
3. **Lower-level sandbox interfaces are not a supported substitute.** The
   [`sandbox-exec` manual mirror](https://keith.github.io/xcode-man-pages/sandbox-exec.1.html)
   and [`sandbox_init` manual mirror](https://keith.github.io/xcode-man-pages/sandbox_init.3.html)
   identify those interfaces as deprecated and direct developers to App Sandbox.
   An [Apple-authored macOS 11.3 SDK header mirror](https://raw.githubusercontent.com/phracker/MacOSX-SDKs/master/MacOSX11.3.sdk/usr/include/sandbox.h)
   marks `sandbox_init` and named profiles "No longer supported," deprecated from
   macOS 10.8. This historical header is not verification of a current installed
   SDK. Availability of an executable, profile text or private API would not
   resolve supported deployment or prove per-child enforcement.

These sources establish a concrete mismatch with App Sandbox and a support
problem with the reviewed alternatives. They do not establish a complete native
escape assessment. No exact macOS build, SDK or editor binary identity has been
selected or approved; historical macOS arm64/Neovim 0.11.5 evidence is insufficient.

## Neovim binding findings

The existing unconfined experiment in `internal/nvimui/process.go` explicitly
requests `--listen <owned-root>/startup.sock`. `bootstrap.lua` requires that exact
listener, closes it, then requires only the parent stdio RPC channel. Therefore
this adapter cannot simply be reused under entry-time no-new-IPC enforcement.
No writable-directory exception should be introduced to accommodate it.

Fresh inspection of [Neovim 0.11.5 `server_init`](https://raw.githubusercontent.com/neovim/neovim/v0.11.5/src/nvim/msgpack_rpc/server.c)
adds an important distinction: absent/empty `--listen` still attempts an
autogenerated listener, but its failure is nonfatal; explicit listener failure
is fatal to server initialization. This suggests a future source-level avenue
once a viable boundary exists, **not tested confined-startup compatibility**.
No listener/launcher/bootstrap change is justified by that fact alone.

The first draft-bearing call is `__sp_ui.init` in `internal/nvimui/session.go`,
after public bootstrap validation. A future backend must establish enforcement
before that call is transmitted, not merely before its reply. The existing
`ownedProcess` retains direct-child pipes/kill/reap ownership, but process groups,
null stderr, explicit environment and a Lua welcome do not establish containment.
There is no supported, externally evidenced late-activation path established
here; harmless startup followed by a child acknowledgement is insufficient.

## Decision needed before implementation

Keep macOS protected opening unavailable. The smallest proposed external step is
**manual Apple DTS clarification**, not another native launcher trial. A
[submission-ready request](macos-editor-sandbox-dts-request.md) is prepared for
the user to submit outside pi; it has not been submitted:

> Is there a supported macOS mechanism for a separately owned command-line
> helper, with only parent-owned anonymous pipes, that denies all filesystem
> persistence including its own container and temporary locations, denies new
> processes and unauthorized network/Mach/XPC/Unix IPC, and excludes inherited
> writable or proxy capabilities before receiving private data? What supported
> API/deployment model establishes this for the exact process?

A positive answer needs public technical documentation and a specified OS/SDK/
editor build before implementation/proof planning can proceed. No support request
was submitted. Public forum human-verification encountered by the feasibility
worker was not pursued; any follow-up there is manual outside pi. Changing the
platform or accepting deprecated/private interfaces would be a separate scope
and support decision, not an implicit continuation or weaker fallback.

## Conditional manual synthetic proof matrix

Only after a mechanism is justified; **outside pi only**, on one recorded exact
OS/build/editor binary/policy combination. Use owned disposable fixtures and
random synthetic data, no normal stores/configuration or plaintext transcripts.

| Unit | Required independent observations |
| --- | --- |
| Admission/binding | Missing or mismatched enforcement refuses private transmission; partial startup/cancellation retains the exact owner. |
| Usable startup | Editing works over owned pipes without writable directory exceptions or startup listeners. |
| Persistence | Ex, Lua, libuv/native I/O, create/append/rename, writable mappings and filename/xattr channels fail against owned targets, including synthetic container/tmp targets. |
| Inherited capabilities | Unauthorized writable/directory FDs, connected sockets, mappings and synthetic Mach/service rights cannot survive admission or be acquired by transfer. |
| Processes | Owned fork/spawn/exec/shell/job attempts fail; no pre-activation helper survives with a plaintext-capable route. |
| IPC/proxies | Owned loopback, Unix and Mach/XPC observers receive no unauthorized payload, including existing-channel/proxy attempts. |
| Encrypted save | Edit/undo/freeze/save remains usable; parent decrypts and compares exact saved bytes in fixture memory and preserves a concurrent shared append. |
| Recovery/ownership | Changed cancellation after relock uses the pinned recovery recipient; conflicts and scripted recovery failure retain ownership through explicit successful retry. |

Validate each negative fixture's observer/target independently first. Child errors,
absent canaries, signatures and sandbox-status columns alone are insufficient.
Record installation and exact-process/transport binding evidence and observation
limits. A blocked startup is not success. A host sandbox denial is final: stop,
do not diagnose/retry/alternate-launch, and ask for the intended manual operation
outside pi.

## Evidence limits

Three same-provider scoped workers completed backend feasibility, read-only
Neovim binding and read-only security reviews. Only the feasibility worker had
public web tools; the parent freshly inspected the Apple pages, SDK header and
Neovim source cited above. The other two reviews are repository source reviews,
not fresh platform-document verification or independent audits. No backend,
adapter, native trial, real-note routing, default change or commit resulted.
